# 愿景与设计理念

## Auralis 是什么

Auralis 是一个**异步优先的反应式内核**，由两个最小化 crate 构成：

- `auralis-signal`：`Signal<T>` + `Memo<T>`，零依赖
- `auralis-task`：`TaskScope` + 优先级执行器，仅依赖 `auralis-signal`

核心理念用一句话概括：

> **反应式 = 可暂停的异步任务；生命周期 = 所有权 + 结构化并发。**

## 为什么存在

传统的反应式编程要求学习一套全新的运行时词汇——effect、cleanup、派生状态图、调度器 tick。Auralis 将其还原为 Rust 开发者已经掌握的概念：

- **`await signal.changed()`**：任务挂起直到值发生变化
- **`TaskScope` 拥有任务**：drop scope 即取消其中的一切
- **事件/定时器/fetch 就是 future**：用 `select!`、`join!` 组合

不需要 `on_cleanup` 钩子，不需要手动 cancel token，不需要"effect 系统"。纯异步 Rust。

## 适用场景

Auralis 不是专门为 Web 或 Wasm 设计的 —— 它适合任何需要"信号变化 → 异步任务响应 → 自动清理"的场景：

- **Wasm UI 框架的底层内核**（配合现有 DOM 库）
- **游戏引擎的事件系统**
- **IoT 传感器数据流处理**
- **服务端 WebSocket 连接管理**
- **任何异步反应式数据管线**

## 核心设计决策

### 1. 延迟回调模型

`Signal::set` **不同步调用 subscriber callback**。它把通知闭包推到执行器的延迟回调队列中，在下一次 flush 开始时执行。

**为什么：** 这彻底消除了重入问题。传统反应式系统需要 `pending_unsubscriptions`、`traversal_depth` 计数器等复杂保护来防止 set-in-set、subscribe-during-callback 等问题。延迟执行让这些问题不复存在。

**代价：** 多一次微任务的延迟。对于绝大多数场景这个延迟可以忽略不计。

### 2. 主动 Waker 注销

`SignalChangedFuture` 被 drop 时，**立即**从 signal 的 subscriber 列表中移除自己的 waker，而不仅仅依赖 `alive` 标志位的惰性检查。

**为什么：** 防止"僵尸 waker 堆积"——这是异步反应式系统中最常见的 bug 之一。如果只依赖惰性清理，在大量创建/销毁 future 的场景下（如 UI 列表虚拟滚动），waker 会在 subscriber 列表中不断积累，导致内存泄漏和性能下降。

### 3. 单线程设计（`!Send` / `!Sync`）

`Signal<T>` 和 `TaskScope` 使用 `Rc<RefCell<...>>` 而非 `Arc<Mutex<...>>`，天然 `!Send + !Sync`。

**为什么：**

- **性能**：`Rc` 是简单的指针操作，`RefCell` 没有原子开销。在 Wasm 单线程环境下，`Arc`/`Mutex` 的原子操作是纯粹的浪费。
- **安全**：没有死锁风险，没有数据竞争。
- **简单**：API 不需要 Send/Sync bound 传染。

**多线程场景怎么办？**

Auralis 的 escape hatch 是 **实例隔离**，而非共享可变状态：

```rust
// 每个线程 / 每个请求一个独立的 Executor 实例
let ex = Executor::new_instance();
let scope = TaskScope::with_executor(&ex); // 显式所有权
scope.spawn(async { /* ... */ });
// scope 持有 ex 的强引用；drop 时在 ex 上取消
```

这类似于 tokio 的单线程 runtime + 多实例并发模型，或 Erlang 的轻量进程 + 消息传递模型。

对于更简单的场景（如工作线程向 signal 喂数据），`std::sync::mpsc` channel + drain 循环只需六行代码——参见 `auralis-task` 的 `examples/multi_thread_bridge.rs`。

**明确不做的：** 不会把 `Rc` 换成 `Arc`、`RefCell` 换成 `Mutex` 来换取"看起来通用"。那是为了形式上的 Send/Sync 而牺牲实际性能，得不偿失。

### 4. Memo 惰性求值 + 一次 compute

`Memo::new(compute)` 在执行期间安装 observer，**只调用一次** `compute`：同时完成初始值计算和依赖发现。

后续源信号变化时，memo 只标记 dirty（一次 Cell 赋值），不重新计算。实际计算推迟到 `read()` 或 `with()` 被调用时。

**为什么：** 惰性求值避免了不必要的计算（两个源信号连续变化时只算一次），一次性 compute 避免了用户对"纯函数"假设的依赖。

### 5. Memo panic 安全（旧订阅保留）

`Memo::recompute` 在 compute 函数 panic 时，**保留旧的源信号订阅**，只清理半成品新订阅。Memo 保持"连接"状态，下次成功 `read()` 即可恢复。

**为什么：** 如果没有这个保证，一次 panic 会让 memo 进入"失聪"状态——与所有源信号断开、无法响应变化、所有 downstream watcher 永久阻塞。保留旧订阅意味着 panic 是可恢复的异常状态，而非不可逆的损坏。

### 6. 迭代式 Scope 取消（BFS + 叶到根）

`TaskScope` 被 drop 时，使用 BFS 收集所有子孙 scope，然后从叶到根取消。明确避免递归，防止深层嵌套 UI 树导致栈溢出。

CallbackHandle（用于 signal subscription 等）在 task 之前被 drop，确保回调链先于 DOM 效应任务断开。

## 不做什么

- **不提供 DOM/渲染层**。Auralis 是纯内核，配合任何 DOM 库使用。
- **不提供 UI 宏**。`view!` 宏、`#[component]` 等不是这个项目的范围（仅提供
  `provide_context!` / `consume_context!` 等最小便利宏）。
- **不提供路由/CLI**。这些是上层框架该做的事。
- **不追求 Send/Sync**。实例隔离是推荐的多线程方案，不需要共享可变状态。

## 运行时特性

除了核心反应式基元，Auralis 还提供以下开箱即用的能力：

- **时间预算可配置**：`set_global_time_budget(ms)` 或 `Executor::set_time_budget(&ex, ms)`，适配不同帧率（60fps / 144fps）或无限制（服务端）
- **任务 panic hook**：`set_panic_hook(hook)` 注册回调，捕获 task 的 panic 信息（task_id、scope_id、payload），用于日志/监控/告警
- **`Signal::map` 轻量投影**：不经过 observer 系统的只读映射，适合 `.len()`、`.field` 等零成本投影
- **`Signal::ptr_eq`**：判断两个 Signal 是否指向同一实例
- **`CallbackHandle::noop()`**：创建空 handle 占位
- **`Signal<T: Default>`**：提供 `Default` 实现
