# 架构与模块设计

## 整体结构

```
auralis/
├── crates/
│   ├── auralis-signal/    # Signal<T>, Memo<T>, batch(), 变更检测 future
│   ├── auralis-task/      # TaskScope 树, 优先级执行器, 取消, 上下文
│   └── auralis-devtools/  # 诊断 DevTools：JSON 快照、变更流、CLI
├── tests/                 # 跨 crate 集成测试
├── examples/              # 可运行示例
└── docs/                  # 设计文档
```

## auralis-signal：反应式基元

### 模块

| 文件 | 职责 |
|------|------|
| `signal.rs` | `Signal<T>` 核心：值存储、版本追踪、subscriber 管理、延迟通知状态机 |
| `memo.rs` | `Memo<T>`：惰性自动追踪计算信号，observer 守卫、panic 安全重算 |
| `batch.rs` | `BatchGuard`、`batch()`、`in_batch()`：批量更新，panic 安全 |
| `observer.rs` | `ObserverState`、`OBSERVER` thread-local：Memo 依赖追踪基础设施 |
| `future.rs` | `SignalChangedFuture`、`MapChangedFuture`、`FilterChangedFuture`：主动 waker 注销 |
| `registry.rs` | 线程局部响应式节点注册表，为 `dump_reactive_graph()` 提供数据（`diagnostics` feature 控制） |
| `lib.rs` | Crate root，公共 API 重导出 |

### 状态机

**Signal 内部状态**（`SignalState<T>`）：

```
set(val) ──► value ← val, version += 1
              ├─ notifying? → dirty = true, return (重入保护)
              ├─ dirty? → return (已调度)
              └─ else → dirty = true, 收集 subscriber, schedule_notification()

notification:
  ├─ dirty = false, notifying = true
  ├─ 遍历 subscriber（跳过 alive=false）
  ├─ notifying = false
  └─ dirty? → 重新调度（回调中发生了 set）
```

**Batch 机制**：

```
batch(f):
  BATCH_DEPTH += 1
  f()
  如果是外层: flush 所有 batched notifications → executor
```

嵌套 batch 由内层忽略，只有最外层执行 flush。

### Observer 机制

Memo 的依赖追踪通过 `thread_local!` 的 `OBSERVER` 实现：

1. Memo 在计算前安装 `ObserverState`（包含 dirty_callback、on_subscribe 闭包、去重用的 `HashSet<SignalKey>`）
2. 计算过程中每次 `Signal::read()` 检测到 observer → 自动订阅
3. 计算结束后通过 `ObserverGuard` 恢复前一个 observer（支持嵌套 memo）

**为什么用 thread_local 而非显式依赖图：** 更简单，依赖关系隐式表达。代价是依赖追踪只在同步计算期间有效——但这恰好是 memo 的使用场景。

## auralis-task：异步任务运行时

### 模块

| 文件 | 职责 |
|------|------|
| `executor.rs` | 单线程执行器：双优先级队列、timer 队列、时间预算、延迟回调/操作、slot 式 waker 路由、实例隔离 |
| `scope.rs` | `TaskScope` 树：父子关系、迭代取消、暂停/恢复、上下文 DI、`CallbackHandle` |
| `timer.rs` | `timer::sleep()` 协作延迟、带 deadline 重检的 `SleepFuture` |
| `debug.rs` | `dump_reactive_graph()` — 统一的响应式图快照，包含 signal、memo 和 task 信息（`debug` feature） |
| `lib.rs` | Crate root，公共 API + `Priority` 枚举 |

### 执行器架构

```
flush() ──► Executor::flush_instance(&global_executor)
               ├─ Step 0: drain 过期 timer（无 TimeSource 时全部过期）
               ├─ Step 1: 执行 deferred ops（set_deferred 等）
               ├─ Step 2: drain deferred signal callbacks（有时间预算，catch_unwind 隔离）
               └─ Step 3: 主 poll 循环
                   ├─ 高优先级队列先出队
                   ├─ 取出 future（避免 borrow 冲突）
                   ├─ 注入 scope + task id（供 timer::sleep），catch_unwind，poll
                   └─ 超预算 → 调度续帧
               └─ drain PENDING_WAKES（借冲突时的缓冲唤醒）
```

**设计要点：**

- **"借出再 poll"模式**：poll 前把 future 从 `tasks` 槽中临时取出，避免在执行器 RefCell 被借用时执行嵌套操作
- **TaskWaker**：存储 `(task_id, slot_id, generation)`，通过线程局部 `Vec<Slot>` 表路由唤醒，generation 计数器使旧 waker 在执行器销毁后自动失效
- **Timer 队列**：`BTreeMap<deadline_ms, Vec<TaskId>>`，在 Step 0 检查。每个 `TaskState` 有 `timer_deadline` 反向索引，task 取消时 O(1) 清理。无 `TimeSource` 时所有 timer 在每次 flush 过期
- **时间预算**：默认 8ms，适合浏览器帧预算。通过 `TimeSource` trait 可插拔
- **实例执行器**：`Executor::new_instance()` 创建完全隔离的执行器，用于 SSR 多请求隔离

**信号路由约束：**

全局调度钩子（`init_flush_scheduler`）和 `schedule_callback` / `set_deferred` 等函数
现在使用 `current_executor_instance()`，优先检查当前 `with_executor` 上下文，
不存在时降级到全局执行器。对于多实例用户：

1. 必须至少调用一次 `init_flush_scheduler`（否则 `set` 会退化为同步执行）。
2. `with_executor` 设置当前执行器，在其作用域内的信号回调和 `set_deferred` 调用会路由到该实例。

对于单线程场景（Wasm、游戏循环、CLI），无需特殊处理：启动时调用一次
`init_flush_scheduler`，不使用 `with_executor` 即可。

### TaskScope 树

每个 scope 持有 `Rc<RefCell<Executor>>` 强引用，执行器至少与 scope 同寿——
保证 drop 时的安全取消。

```
TaskScope::with_executor(&ex)    # 显式执行器，主 API
TaskScope::new()                 # 便利入口：委托到全局执行器
├─ scope_1.spawn(future_a)       # 通过 scope_1 的执行器路由
├─ child = scope_1.new_child()
│   └─ 继承父 scope 的执行器
└─ drop(scope_1)
    ├─ CallbackHandle 先 drop（断开信号链）
    ├─ BFS 收集 scope_1 + child
    ├─ 每个 scope 调用 cancel_scope_tasks_on(&scope.executor, id)
    └─ 叶到根取消所有 task（在正确的执行器上）
```

**取消流程：**

1. `TaskScopeInner::drop()` 触发
2. BFS 遍历 → 收集所有子孙 scope id 到 `VecDeque`
3. 反转（`into_iter().rev()`） → 从叶到根的顺序
4. 对每个 scope：
   a. 设置 `cancelled = true`
   b. drop 所有 `CallbackHandle`（放在 drop 守卫中，先于 task 执行）
   c. 调用 `executor::cancel_scope_tasks(scope_id)` 移除所有 task
5. 注销 scope registry 中的所有条目

**为什么不递归：** 200 层 UI 树在递归 drop 时会栈溢出。BFS + 迭代避免了这个风险。

### Scope 暂停/恢复

- `suspend()` 级联：暂停父 scope 会暂停所有子 scope
- 暂停时 task 仍在 tasks 表中，但 poll 循环检查 `is_suspended()` 会跳过
- `resume()` 级联恢复并重新入队所有 task

### 上下文系统

类型安全的依赖注入：

```rust
scope.provide(42i32);                    // 存入 i32
let val: Option<Rc<i32>> = scope.consume(); // 取出，沿父链向上查找
let val: Rc<i32> = scope.expect_context();  // 同上，找不到则 panic
```

子 scope 的值会遮蔽父 scope 的同类型值。

## 诊断基础设施

Auralis 提供内置的内省能力，用于调试响应式系统：

### 标签

`Signal`、`Memo` 和 `TaskScope` 各自带有一个可选的标签（短字符串），
会出现在 `Debug` 输出和 `dump_reactive_graph()` 中。标签始终可用——
每个节点的额外开销仅为一个 `Rc<RefCell<Option<String>>>`。

```rust
let sig = Signal::new(0);
sig.set_label("counter");
assert_eq!(sig.label(), Some("counter".to_string()));
```

### 响应式节点注册表

通过 `diagnostics` feature（由 `auralis-task` 的 `debug` feature 自动启用），
每次 `Signal::new` 和 `Memo::new` 会把一个回调注册到线程局部的注册表中。
回调捕获了节点内部状态的 `Weak` 引用；已死亡的节点（被 drop 的 signal/memo）
会被自动清理。

`dump_registry()` 返回 `Vec<ReactiveNodeSnapshot>`，包含每个存活节点的
label、version、subscriber 数量、dirty 状态（memo）、compute 次数和依赖数。

### 调度观察者

`add_schedule_observer(Box<dyn Fn()>)` 注册一个被动钩子，在每次 signal 变更
（`set`、`update`、`bump_version`）时触发。支持多个观察者共存。基于代际
（generation）的 `ObserverToken` 防止旧 token 误用。每个观察者独立
`catch_unwind` 隔离，重入调用被静默跳过。

### `dump_reactive_graph()`

统一的诊断输出（需 `auralis-task` 的 `debug` feature），在一个快照中展示
所有 signal、memo 和 task：

```text
=== Auralis Reactive Graph ===
Signals: 3  Memos: 2  Tasks: 4

── Signals ──
  "counter"  ver=42  subs=1  addr=0x...
  (unnamed)  ver=7   subs=0  addr=0x...

── Memos ──
  "sum"  ver=42  subs=1  dirty=false  computed=15x  deps=2  addr=0x...

── Tasks ──
Scope 1 "root":
  task 0  [L]  queued
```

`dump_task_tree()` 仍然可用，作为向后兼容的别名。

## auralis-devtools：检查与诊断

### 模块

| 文件 | 职责 |
|------|------|
| `snapshot.rs` | `ReactiveSnapshot` 结构体、`snapshot()` — 调用 `dump_registry()` 并格式化为 JSON 可序列化快照，包含 memo 依赖地址 |
| `stream.rs` | `ChangeReceiver`、`change_stream()` — 安装调度观察者，通过 `mpsc` channel 传递变更事件，支持高效的 `wait_timeout()` 阻塞等待 |
| `main.rs` (bin) | CLI：`dump`（一次性 JSON 输出到 stdout）、`stream`（变更事件流）、`serve`（WebSocket 服务，需要 `ws-transport` feature） |

### 数据流

```
Signal 变更 → notify_schedule_observers()
  → change_stream observer 递增 seq + mpsc send
  → ChangeReceiver::wait_timeout() 唤醒
  → 调用者调用 snapshot() → dump_registry() → JSON
```

### CLI 用法

```bash
# 一次性快照
cargo run -p auralis-devtools -- dump

# 管道友好的变更流
cargo run -p auralis-devtools -- stream

# WebSocket 服务（需要 ws-transport feature）
cargo run -p auralis-devtools --features ws-transport -- serve
```

## Feature flags

| Feature | 所属 Crate | 启用内容 |
|---------|-----------|---------|
| `debug` | `auralis-task` | `dump_reactive_graph()` + 响应式节点注册表（转发到 `auralis-signal/diagnostics`） |
| `diagnostics` | `auralis-signal` | 响应式节点注册表、`ReactiveNodeSnapshot`、`dump_registry()` |
| `ssr-tokio` | `auralis-task` | `init_scope_store_tokio()` 为 tokio task-local 存储 |
| `ws-transport` | `auralis-devtools` | WebSocket 服务（`auralis-devtools serve` 命令，额外引入 `tungstenite`） |
